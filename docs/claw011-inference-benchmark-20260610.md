# Qwen3.6-35B-A3B 自建 vLLM 推理性能测试报告

**测试对象**:GPU 工作站自建 vLLM 推理服务
**业务负载**:ClawOps 智能体租户 claw-011(企业服务 IM 机器人)
**数据来源**:claw-011 生产运行日志 `runtime-trace.jsonl`,2026-06-10
**模型**:Qwen3.6-35B-A3B(MoE,激活约 3B),`max_model_len = 250000`
**推理端点**:`http://220.203.247.222:8011/v1`(OpenAI 兼容)
**报告日期**:2026-06-17

---

## 0. 结论摘要

基于 2026-06-10 全天 claw-011 生产流量(33 次 LLM 调用、32 次成功、14 个用户会话)的实测数据:

1. **本业务是"超长输入、极短输出"的智能体负载**:输入 token 中位数 **108,844**、最高 **249,013**;输出 token 中位数仅 **112**。输入/输出比中位约 **970:1**。
2. **端到端延迟几乎全部由 prefill(预填充)决定**:单次 LLM 调用端到端 p50 = **6.1s**、p95 = **33.7s**;长输出请求里 decode 占比很小,延迟主导项是处理超长输入的 prefill。
3. **prefill 吞吐随上下文增长而下降**:短上下文(13k)约 **20,000 tok/s**,长上下文(237k,9 个样本)稳定在 **~8,280 tok/s**(扣除 decode 后,8,047–8,463 区间)。对应推导 TTFT 从 **0.66s**(13k)升到 **~28–31s**(240k)。
4. **单流 decode(短上下文实测)约 11 ms/token(~90 tok/s)**,对 IM 机器人场景流畅度充足。
5. **前缀缓存效果显著**:同一会话内重复迭代命中 KV cache,247k 上下文的请求从冷启动 **33s** 降到 **2.2–2.5s**,约 **14 倍**加速。
6. **成功率 97%(32/33)**:唯一 1 次失败是上下文超过 250k 上限,属应用层上下文长度问题,已在软件侧修复。
7. **对照 IM 智能体常见 SLA**:短/中上下文(<30k)的 TTFT < 2s 满足要求;长上下文(~240k)TTFT ~28–31s 不满足——该延迟来自 `输入token ÷ prefill吞吐` 的乘积,由输入长度和 prefill 吞吐共同决定(见第 6 节)。

> 数据说明:本批数据为**单并发**(同一时刻仅一个用户、智能体串行调用)、单用户场景;TTFT/TPOT 为基于 `duration_ms` + token 数推导值(日志记录端到端墙钟,无流式首 token 打点)。推导方法见第 4 节。

## 3. 前缀缓存加速(实测,显著正向能力)

vLLM 的 prefix caching 在本业务中效果突出:同一会话内,智能体多轮迭代复用前一轮已 prefill 的 KV cache,只需重算新增的少量 token。三个长上下文会话的冷/热对比:

| 会话 | 冷启动(iter=1) | 缓存命中(后续迭代) | 加速比 |
|---|---|---|---|
| S3 | 226,692 tok → **27,846 ms** | 235,433 tok → 8,435 ms | ~3.3× |
| S10 | 237,810 tok → **29,730 ms** | 244,167 tok → 2,997 ms / 247,154 tok → 6,379 ms | ~10× |
| S11 | 247,572 tok → **33,077 ms** | 248,393 tok → 2,340 ms / 249,013 tok → 2,234 ms | **~14×** |

**结论:在多轮智能体会话中,只有每个会话的首轮承担完整 prefill 成本,后续迭代基本免费**。这显著降低了"工具调用循环"类负载的累计延迟。

## 4. 推导 TTFT 与 prefill 吞吐

### 4.1 推导方法

- **TTFT(首 token 时延)**:取 `iteration=1` 的请求近似"prefill 主导"场景,端到端时间 ≈ prefill 时间 + 极少量 decode;扣除 decode(按 ~15 ms/token × 输出数)后即 TTFT 估值,`输入token ÷ TTFT` = prefill 吞吐。注:vLLM prefix caching 跨请求按前缀块共享,`iteration=1` 仍可能命中系统提示/工具定义等公共前缀,故为近似下限(本数据所有 iter=1 长上下文请求均在 29–35s,无异常快者,说明实际未发生大段命中)。
- **prefill 吞吐列统一采用"扣除 decode"口径**。

### 4.2 推导 TTFT 与 prefill 吞吐(按上下文)

| 上下文输入 token | 样本数(iter=1) | 推导 TTFT | prefill 吞吐(扣除 decode) |
|---|---|---|---|
| ~13,000 | 1(out=2) | ~0.66 s | ~20,100 tok/s |
| ~30,000 | 1 | ~1.9 s | ~15,900 tok/s |
| ~109,000 | 1 | ~9.0 s | ~12,100 tok/s |
| ~237,000(226k–248k) | **9** | **~28 – 31 s** | **8,047 – 8,463 tok/s,中位 8,280** |

> 长上下文档(226k–248k)的 9 个 `iteration=1` 样本,扣除 decode 后 prefill 吞吐紧密聚集在 **8,047–8,463 tok/s(中位 8,280)**,一致性高,是本数据最稳健的硬件吞吐观测。短/中上下文档各仅 1 个 iter=1 样本,作趋势参考。趋势上 prefill 吞吐随上下文增长单调下降(注意力 O(n²) + KV cache 压力),符合预期。

## 5. 推导 TPOT / decode 速度

| 上下文 | TPOT | decode 吞吐(单流) | 数据支撑 |
|---|---|---|---|
| ~13,000 | **~11 ms/token** | **~90 tok/s** | 2 条 decode 主导样本 |

- **短上下文 decode ≈ 11 ms/token** 实测可靠:取 prefill 占比 < 10% 的 decode 主导请求——`13,037 输入 / 740 输出 / 8,908ms` 与 `13,836 输入 / 103 输出 / 1,820ms`,decode 占墙钟 90%+,`duration/output` ≈ 11 ms/token。
- 长上下文请求中 prefill 占墙钟 90%+,decode 仅为残差,**本数据集的负载形态下 decode 时延无法从端到端墙钟中单独分离**,故不在此给出长上下文 TPOT 数值。
- **单流 decode ≥ 90 tok/s 对 IM 机器人场景流畅度充足**(人眼阅读约 10–20 tok/s)。

## 6. SLA 评估(对照 IM 智能体常见目标)

本业务为异步 IM 机器人(飞书/微信),非实时语音。对照该类业务常见 SLA:

| 指标 | 本数据实测/推导 | 常见目标 | 对照 |
|---|---|---|---|
| TPOT(短上下文,单流) | ~11 ms/token | < 50 ms/token | ✅ 满足 |
| TTFT(上下文 < 30k) | < 2 s | < 3–5 s | ✅ 满足 |
| TTFT(上下文 ~240k 冷启动) | ~28–31 s | < 3–5 s | ❌ 不满足 |
| TTFT(上下文 ~240k 缓存命中) | 2.2–2.5 s | < 3–5 s | ✅ 满足 |
| 成功率 | 97%(32/33) | > 99% | 唯一失败为上下文超限,已修复 |

**长上下文冷启动 TTFT 不满足的量化归因**:TTFT ≈ 输入token ÷ prefill吞吐 = `240,000 ÷ 8,280 ≈ 29s`,与实测 ~28–31s 吻合。该乘积由两个因素共同决定——**输入长度**(本业务把工具返回的大 JSON 整段纳入上下文,详见 `docs/bdhrapi-list-api-slimming.md`)与 **prefill 吞吐**(硬件/并行配置)。前缀缓存命中时(同会话重复迭代)该延迟降到 2.5s 以内、转为满足。

> 上述均为单并发单流下的对照;本数据全程并发度为 1。
