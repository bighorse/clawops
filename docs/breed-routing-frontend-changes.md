# 分流品种：前端/客户端侧改动说明

**发给**：小程序团队、企微机器人后端团队
**一句话**：让不同来源进来的用户自动落到不同品种的龙虾上。
**完整契约**见 `breed-routing-integration.md`；本文只讲**你们要改什么**。

---

## 0. 先看这张表：谁要改，改多少

| 团队 | 要改吗 | 改什么 | 工作量 |
|---|---|---|---|
| **小程序前端** | **不用改** | — | 0 |
| **小程序后端** | 可选 | 换 openid 的响应里多返回一个 `breed` | 加一个字段 |
| **企微机器人后端** | **必须改** | 调 `/auth/wecom-login` 时多传一个 `breed` | 加一个字段 |
| ClawOps（我方） | 已完成 | — | 已上线 |

**小程序侧真的不用动代码**，原因见第 1 节。企微侧是唯一必须改的，见第 2 节。

---

## 1. 小程序：为什么零改动

`app_id` **已经**随每次登录传上来了：

```
POST /auth/wx-login
{"app_id": "wxABC123...", "code": "...", "display_name": "...", "avatar_url": "..."}
```

ClawOps 拿到 `app_id` 后转发给你们后端换 openid，所以「这个人来自哪个小程序」
这个信息**在分流点上早就具备**，只是以前没拿来选品种。现在 ClawOps 会用它查一
张配置表决定品种。

### 🚫 千万不要做的事：加一个 `breed` 字段

```jsonc
// ❌ 绝对不要这样
POST /auth/wx-login
{"app_id": "...", "code": "...", "breed": "shangji"}
```

`/auth/wx-login` 是**公网、设备侧**接口，除了按 IP 限流之外**没有任何鉴权**。
品种决定这只龙虾的人格、技能和工具权限——如果由客户端指定，任何人改一下请求体
就能**自选人格、自选技能、自选数据权限**。

ClawOps 侧不读这个字段，传了也没用。**如果哪天代码评审里看到有人加它，那是个
安全问题，不是新功能。**

> 企微那个接口可以传，因为它带管理员令牌、是服务器间调用。**同一个需求，两个
> 接口的正确答案是相反的**——这是这次最容易踩错的地方。

### 可选：小程序后端替 ClawOps 决定品种

默认由 ClawOps 配一张 `app_id → 品种` 的表（运维维护）。如果你们希望这份归属
关系放在自己系统里，可以在换 openid 的响应里多返回一个字段：

```jsonc
// 现在
{"data": {"open_id": "oABC..."}}

// 加上 breed 之后
{"data": {"open_id": "oABC...", "breed": "shangji"}}
```

- **字段可选**，不加 = 行为完全不变，ClawOps 去查自己的配置表
- ClawOps **优先采用**你们返回的值
- 返回 `""` 或空白 = 「我没意见」，不会被当成一个名字为空的品种
- 好处：新增小程序时不用再找运维改 ClawOps 配置

## 2. 企微机器人后端：唯一必须改的地方

### 现状

请求体**只有三个字段**，**没有 corpid、没有 agentid**，没有任何能区分企业或
业务线的信息：

```
POST /auth/wecom-login          （需 X-Admin-Token）
{"uin": "7881303049925005", "display_name": "张三", "avatar_url": "https://..."}
```

所以这边不是「把已有信息用起来」，而是**必须新增字段**。

### 改法

加一个可选的 `breed`：

```jsonc
POST /auth/wecom-login
{
  "uin": "7881303049925005",
  "display_name": "张三",
  "avatar_url": "https://...",
  "breed": "shangji"          // ← 新增，可选
}
```

### 四条你必须知道的行为

| 情况 | ClawOps 的行为 |
|---|---|
| **不传** `breed` | 用默认品种。**与现在完全一致，老代码不改也不会坏** |
| 传了一个**存在**的品种 | 新租户开在该品种上 |
| 传了一个**不存在**的品种 | **返回错误**，且不会创建 Linux 用户、不写数据库 |
| 对**已存在**的用户传了别的品种 | **品种不变**，静默忽略 |

最后一条要特别注意：**登录不会改动已有租户的品种**。这是有意的——改品种会重启
对方的 daemon、并把旧品种的技能从他工作区里删掉，不该由一次普通登录顺带触发。

要给存量用户换品种，用这个接口（运维操作，不是登录流程的一部分）：

```bash
curl -X PUT -H "X-Admin-Token: $TOKEN" -H 'Content-Type: application/json' \
  -d '{"breed":"shangji"}' \
  "$CLAWOPS_URL/admin/users/<openid>/breed"
```

### 品种名从哪来

品种名（如 `shangji`）由运维在 ClawOps 上创建，**不是你们自己起的**。开发前先
问一下当前有哪些品种：

```bash
curl -H "X-Admin-Token: $TOKEN" "$CLAWOPS_URL/admin/breeds"
```

## 3. 联调验收

按顺序过一遍，**第 2、5、6 条最容易被漏**：

| # | 动作 | 期望 |
|---|---|---|
| 1 | 用已配置分流的小程序，登录一个**全新** openid | 落到映射的品种 |
| 2 | 用**未配置**的 app_id 登录新用户 | **能正常登录**，拿默认品种，**不报错** |
| 3 | 企微用**新** `uin` + `breed` 调一次 | 该租户拿到指定品种 |
| 4 | 企微**不传** `breed` 调一次 | 拿默认品种（老行为不变） |
| 5 | 企微传一个**不存在**的品种 | 返回错误，**且没有新建 Linux 用户** |
| 6 | 对**已存在**的用户，带一个不同的 `breed` 再登录一次 | 品种**不变** |

第 2 条防的是「把路由表当白名单」——那会把所有没配置的小程序全锁在门外。
第 6 条防的是「登录顺手改品种」——那会在用户毫无察觉的情况下重启他的龙虾。

## 4. 常见误区

- **别用品种做权限控制。** 品种决定「这只龙虾是什么样」（人格、技能、SOP），
  不决定「这个人能看什么数据」。数据权限仍然靠各租户独立的工作区和后端接口
  鉴权。
- **一个 openid 只属于一个品种。** 同一个人从两个小程序进来，如果 openid 相同，
  后进的那次不会改变他的品种。真要区分，得让两个来源产生不同的 openid。
- **上线顺序不能反：先推品种，再配分流。** 分流配置里写一个还没推过的品种名，
  那个来源的新用户会**直接注册失败**。
